1. VERIFIED FINDINGS AND THEIR IMPLICATIONS

A. Settings exist as scattered controls, but there is no centralized settings experience.
Evidence: src/lib/hunt/store.ts persists layer visibility, opacity, terrain, units and other preferences; HuntApp.tsx places many controls in the Layers panel around lines 1450–1510.
Action: create a settings schema and settings UI using the existing preference values as migration inputs. Keep Layers as a quick map control, with both surfaces connected to the same state.

B. Hunting context is hard-coded to Arizona and Idaho.
Evidence: types.ts declares HuntRegion = "az" | "id"; units.ts uses a two-entry SPECS registry; HuntApp.tsx uses pickRegion, state-specific borders, conditional strings, and import-driven guessRegion behavior.
Action: replace the selected-state dependency with geographic discovery. State boundaries remain data and search filters; they stop being app modes. The underlying map can already display other places, so do not describe this as replacing a state-locked basemap.

C. Offline support is a small tile cache, not a complete field package.
Evidence: tiles.ts sets MAX_PACK_TILES = 220 and accepts a single zoom level, clamped to 8–15. README documents missing dependencies and online-only capabilities. public/sw.js handles the app shell separately.
Action: create verified, resumable multi-layer area packages. Raising the tile cap alone is not a solution.

D. Missing public-land data can be misrepresented as ownership.
Evidence: identifyLand in land.ts returns agency "PVT", label "Likely private", and tone "private" when no usable match exists. Unknown agency codes also default to a public tone. Layers says blank ground is usually private.
Action: preserve unknown, no coverage, and service unavailable states. A missing polygon is not evidence of private ownership; an unfamiliar agency code is not evidence of public access.

E. Weather has missing-value and provenance weaknesses.
Evidence: weather.ts uses num(value, fallback = 0) throughout parsing; absent values can become 0 temperature, calm wind, zero precipitation probability or a clear weather code. The NWS fallback infers cloud percentage from text categories. FieldWeather does not identify provider, issue time, fetch time or field-level provenance.
Action: use nullable measurements and explicit quality metadata. Display unknown as unknown. Label inferred cloud cover and forecast-derived current conditions.

F. Weather is point-based, not a radar/cloud-volume data pipeline.
Evidence: weather.ts requests point forecasts, total cloud cover and precipitation probability; MapCanvas.tsx contains terrain, map and sun rendering but no gridded radar/volumetric cloud system.
Action: add weather grids and time semantics before 3D weather. A day's peak rain probability cannot drive a rainfall-intensity renderer.

G. Shooting-hour calculations are too general for national expansion.
Evidence: HuntApp.tsx around lines 904–905 and 2253–2254 applies AZ_SHOOT_LEAD_MIN around sunrise/sunset; nearby Idaho explanatory text already mentions species-specific differences.
Action: separate astronomical daylight from jurisdiction/species/season rules. Audit existing state guidance too. Do not carry this one offset into a national legal-hours system.

H. Unit cache validity is weak for a national catalog.
Evidence: units.ts accepts a cached result with more than 20 units, prefers cache without age validation, and retains resolved promises in pending. A feature-count threshold is not a nationwide completeness check.
Action: use provider-specific validation, pagination, versioned manifests, timestamps, refresh policies and coverage checks.

I. GPS recording needs durable incremental storage.
Evidence: ensureWatch in HuntApp.tsx appends points to in-memory refs/state, using an eight-meter movement threshold; completed/error-stopped tracks are saved. TrackPoint only stores coordinates and time.
Action: checkpoint active sessions transactionally, retain accuracy/fix timestamps, handle gaps, and recover after process termination. Current geolocation support does not establish reliable locked-screen recording.

J. Main UI and renderer concentrate too much responsibility.
Evidence: HuntApp.tsx is approximately 2,447 lines; MapCanvas.tsx approximately 1,233 lines.
Action: extract bounded feature modules when each phase needs them. Avoid an unrelated wholesale rewrite.

K. Parcel owner names and cloud sync are absent by design in current documentation.
Action: build coverage-aware parcel adapters and portable backups. Nationwide ownership completeness is a data acquisition and maintenance problem, not something a coding agent can manufacture.

Implementation:
- Define a typed, versioned AppSettings object and runtime validator.
- Give every persisted setting a default, valid range, migration behavior and effect.
- Resolve effective values as defaults + user preferences + optional active preset + temporary session overrides, with a visible reason for automatic performance changes.
- Presets: Field/battery saver, Scouting/terrain, Weather, Custom.
- Applying or editing a preset must not erase the user's underlying preferences.
- Reset a category independently. Resetting preferences must not delete marks, tracks or offline packages.
- Reject invalid imported values; preserve valid data; never import credentials through ordinary settings exports.

Acceptance:
Every setting affects real behavior, survives restart, has an accessible label and can be reset. Quick Layers and Settings remain synchronized. Export/import round-trips. Old saved preferences migrate without changing the user's established units or map view.

6. NATIONWIDE GEOGRAPHY AND DATA CATALOG

Remove compulsory Arizona/Idaho mode selection. Do not replace the union with fifty branches. Keep state and agency information as provider metadata and optional filters.

Provider discovery:
- Query a small coverage index for the current viewport, selected point or search result.
- Load only intersecting sources relevant to zoom and active layers.
- Use stable IDs including jurisdiction, agency, dataset and source feature ID.
- Support overlapping species/season unit systems and multiple results at a point.
- Preserve polygon holes and multipart geometries.
- Support Alaska's antimeridian crossings with split query bounds and wrapped rendering.
- Avoid one continental bounding box that excludes Hawaii or the Aleutians.
- Use geodesic distance/area calculations; do not interpret longitude degrees as meters.

Illustrative contracts, to adapt rather than copy blindly:

LayerDescriptor:
  id, title, category, geometryType, coverageGeometry, minZoom, maxZoom,
  providerId, sourceUrl, attribution, licenseUrl, retrievedAt, sourceUpdatedAt,

ProviderCapabilities:
  view, identify, search, download, redistribution, maxZoom,
  geographicCoverage, timeCoverage, attribution, rateLimitPolicy

  id, jurisdictionId, providerId, sourceFeatureId, label, speciesTags,
  seasonContext, geometryReference, sourceVersion, validity, sourceUrl

DataStatus:
  available | partial | unavailable | unknown | stale

Do not conflate unavailable, empty and not-yet-loaded.

Nationwide layers:
- Basemap, terrain, hydrography and roads using permitted sources.
- National land-management/protected-area context, supplemented by local agencies.
- Hunting units and species-specific zones through authoritative state/tribal adapters.
- Parcels and owner details only where sources and rights support them.
- Access restrictions, closures and seasonal road designations as separate overlays.

Candidate data families:
- USGS PAD-US for protected-area/management context, not parcel ownership or hunting permission.
- BLM surface-management sources already used by Fieldline.
- State wildlife GIS and official regulations links.
- County/state open parcel GIS with explicit reuse and freshness metadata.
- USFS travel-management/closure sources, agency trailheads and public access programs.
- USGS elevation/imagery and OSM-derived roads/trails under suitable terms.

These are candidate families, not a claim that every jurisdiction offers complete or unrestricted data. Maintain a provider register with verified URLs, capabilities, rate policies, licensing and unsupported regions. Audit all 50 states and DC; ship a truthful coverage matrix.

Ingestion:
- Fetch metadata before downloading features.
- Honor pagination, transfer limits, field mappings and source coordinate systems.
- Validate geometry, bounds, feature counts against source metadata, and plausible changes between versions.
- Quarantine suspicious updates rather than replacing good data with an empty response.
- Store raw-source provenance and deterministic transformation settings.
- Build vector tiles or partitioned packages for large datasets; small GeoJSON is acceptable for early adapters.
- Keep precise identify geometry or an authoritative query path separately from simplified display geometry.
- Use a spatial index for local identification. Do not download every state's geometry at startup.
- Use interior label points rather than averaging polygon vertices.
- Refresh with versioned manifests and bounded conditional requests.
- Add new jurisdictions primarily through adapters/configuration, without editing the app shell.

Coverage acceptance:
Cross a state line without mode switching; adjacent unit layers remain visible and searchable. Test Arizona–Utah, Idaho–Montana, an eastern-state boundary, Alaska and Hawaii. Search nationwide with optional jurisdiction filters. Selecting a known unsupported area says which layer is unavailable. No empty result becomes an ownership or access conclusion.

7. OWNERSHIP, ACCESS AND HUNTING RULES

Model these independently:
- Ownership: who owns land, if known.
- Management: responsible agency.
- Public access: permitted, conditional, restricted, unknown.
- Hunting permission: supported context and official reference.
- Current restrictions: dates, closures, permits, species and weapon context.

Public land does not automatically mean open hunting. A road or trail line does not establish a public right-of-way. Conservation easements do not automatically permit entry. Tribal lands require their own authoritative context.

Point inspection should return multiple relevant records with source dates, rather than silently selecting a single record solely because its polygon has the smallest area. Explain ambiguity near borders. Preserve current map attribution.

Correct land.ts no-match and unknown-code behavior first. Add explicit tests for empty success, provider failure, unrecognized agency, overlapping polygons and known private data. Display "Ownership unknown" or "No coverage" as appropriate. Remove blanket UI text that all owner names require a paid dataset; availability varies.

Legal-hours design:
- Compute sunrise, sunset and twilight as astronomy, independent of hunting regulations.
- Resolve any legal rule by jurisdiction, species, season, method and date.
- Include source URL, effective dates, checked date and applicability.
- If no verified rule applies, show daylight only and a link to the responsible agency.
- Do not fabricate an AI summary of regulations as authoritative guidance.
- Test DST transitions, Arizona and Navajo Nation time-zone distinctions, state boundaries, and Alaska polar-day/night cases.
- A user's custom time offset remains a personal planning setting.

The implementation agent must check current official sources when adding rules. This document deliberately does not assert the current law for any state.

8. STORAGE, BACKUPS AND OFFLINE FIELD PACKAGES

User data:
- Preserve fieldline-v1 as a migration source.
- Move growing tracks, attachments and package metadata to IndexedDB or a tested platform repository.
- Retain the original source until the new transaction commits and verification succeeds.
- Use migration versions, idempotent steps, validation and recovery.
- Never overwrite unreadable saved content with defaults.
- Separate settings reset, cache clearing and personal-data deletion.
- Provide a complete Fieldline backup containing settings, projects, waypoints, tracks and attachment metadata/content as supported.
- GPX remains interoperable export, but does not replace a complete backup.
- Test duplicate imports, interrupted restore, unsupported future versions, quota failures and corrupt archives.
- Bound archive sizes and paths; guard against path traversal, decompression bombs and unsafe XML/HTML.

Offline package:
Select a rectangle, polygon or route corridor. Show estimated size, zoom range, included layers, missing capabilities and source versions before downloading.

A package manifest includes:
  packageId, schemaVersion, bounds/geometry, createdAt, sourceVersions,
  zoomRange, layerIds, requiredAssets, checksums, expectedBytes,
  actualBytes, progress, integrityStatus, expiryPolicy, attribution

States:
  planned -> downloading -> paused/failed -> verifying -> ready
  ready -> stale -> updating -> verifying -> ready
Keep the old ready package usable until an update commits successfully.

Include all dependencies required for claimed offline behavior: style, tiles, glyphs, sprites, terrain if selected, boundary/identify data and a local search index if offered. Bundle app-shell resources separately and verify cold startup.

Use PMTiles or another suitable archive format where it fits the delivery/storage model. PMTiles is a tile container, not automatic offline support: HTTP range caching does not guarantee a complete downloadable area. Explicitly design local random access, subset generation, checksums and asset dependencies. Evaluate MBTiles for desktop only if the benefit justifies a native/database dependency.

Provider policy:
- Enable download only for sources whose terms permit it.
- Source viewing permission does not imply bulk-download or redistribution permission.
- Supply a usable permitted offline basemap option when the user's current imagery cannot be downloaded.
- Do not use the standard OSM tile service for bulk prefetch.
- Verify Esri, USGS, OpenFreeMap and other source terms separately; do not apply one provider's rules to all.
- Do not attempt a nationwide high-resolution download as the default.

Storage behavior:
- Request persistent browser storage where supported, report the result, and remain honest about eviction risk.
- Enforce byte budgets, pin field packages, deduplicate shared assets and maintain reference counts.
- Deleting one package must not break another.
- Recover paused downloads after restart. Use bounded concurrency, backoff and cancellation.
- Make storage failures visible before claiming success.
- Desktop packages may use the filesystem through a narrowly scoped adapter, never arbitrary renderer filesystem access.

Acceptance:
After download and verification, terminate the app, disable networking, reopen it and use every advertised layer at every advertised zoom. Inspect marks, identify included features, record a track and reopen it. Test one missing asset, corrupt chunk, expired source, full disk, interrupted update and shared-package deletion. A partly downloaded package cannot display "Ready."

9. NAVIGATION AND FIELD RELIABILITY

Build a location service independent of the UI:
- Fix timestamp, horizontal accuracy, nullable altitude/vertical accuracy, speed and heading.
- Distinguish GPS movement heading from device compass heading.
- Reject invalid/stale fixes and flag implausible jumps.
- Preserve raw samples when practical; smoothing must not rewrite the source silently.
- Use adaptive recording with time/distance/accuracy criteria rather than distance alone.
- Mark gaps as separate track segments; do not draw a fabricated continuous route through lost signal.
- Persist incremental chunks and active-session state. Recover after a crash.
- Pause/resume/stop are explicit; transient signal loss should not unnecessarily terminate a session.
- Give recording and battery status priority over visual effects.

Guidance:
- Navigate to a waypoint, reverse a recorded track, return to camp/car, and measure distance/bearing.
- Distinguish straight-line bearing from a routed traversable path.
- Add planned routes, elevation profiles and route alternatives after data availability is established.
- Trail snapping is optional; retain a manual route mode.
- Use known access restrictions in routing and identify unknown segments.
- Do not infer legal access from OSM road classification alone.
- Boundary/off-route alerts must account for accuracy and data uncertainty, avoiding false precision.

Mobile:
Responsive PWA support is useful, but browser installation does not guarantee reliable background GPS, lock-screen recording or persistent storage on every phone. Validate on real iOS and Android devices. If long locked-screen recording is a release requirement, create an architecture decision for a native-capable mobile shell/location service; do not claim a PWA solves it. Keep domain logic and file formats reusable.

10. WEATHER DATA MODEL AND PIPELINE

Use three distinct product types:
- Observations: radar, stations, satellite retrievals.
- Forecasts: model data for specific valid times.
- Visual approximations: interpolated shapes or unavailable cloud-height substitutes.

Never label a forecast as an observation. Never turn probability into rainfall rate.

Units:
- Radar reflectivity is commonly dBZ.
- Rainfall rate is usually mm/h or in/h, not inches per minute.
- Accumulation is mm/in over a stated interval.
- Precipitation probability is a percentage.
- Cloud cover is an area fraction/percentage.
Each has a separate type, legend and renderer input.

Normalized WeatherFrame:
  id, providerId, productId, kind, modelRunAt, issuedAt, validAt,
  intervalStart, intervalEnd, fetchedAt, expiresAt,
  units, gridProjection, gridTransform, bounds, nativeResolution,
  mask, qualityFlags, values, attribution, provenance

Do not require all fields to be non-null when the source does not provide them; record unknown explicitly. Keep source resolution distinct from interpolated display resolution.

WeatherSample:
  location, validAt, temperatureC?, windU?, windV?, gustMps?,
  cloudLow?, cloudMid?, cloudHigh?, precipitationRateMmH?,
  precipitationAmountMm?, precipitationType?, cloudBaseM?,
  cloudTopM?, heightReference?, measurementQuality

Question marks mean absent data, not zero.

Provider approach:
A. Keep/refactor point forecast providers for the weather card and selected-point timeline. Add real precipitation amounts and cloud layers where documented.
B. Add a conventional radar overlay through a verified NOAA/NWS radar service or compatible licensed source.
C. For numeric intensity, use a documented quantitative raster/grid product; an attractive precolored radar image is not automatically a numeric input.
D. Evaluate NOAA MRMS precipitation products and suitable model grids for spatial weather. Validate actual domain coverage and product availability; do not assume a CONUS product covers Alaska/Hawaii.
E. For initial cloud visualization, use a bounded coarse grid of forecast samples only if provider request budgets permit it. Label it interpolated forecast cloud cover. Do not query one point per render cell.
F. At scale, use a small reproducible preprocessing job to decode/subset/reproject numeric weather into cacheable tiles. Bound retention and compute. Keep point-only mode when this infrastructure is unavailable.
G. Later, evaluate GOES cloud-top/optical products as additional constraints, not a complete measurement of every hidden cloud layer.

Time:
- Store instants in UTC and display the forecast location's IANA zone by default.
- Preserve interval semantics. Convert an interval accumulation to an average rate only with the correct duration and an explicit label.
- Keep observed and forecast sections distinct on the time slider.
- Do not interpolate across large missing time gaps or incompatible model runs.
- Scrubbing time must synchronize radar, clouds, precipitation, wind and point readouts; otherwise show individual timestamps.
- Show issue time, valid time, age, source and gaps.

Network:
- Cache by provider/product/grid tile/time/model run.
- Deduplicate requests, cancel stale viewports and honor Retry-After.
- Use provider-specific refresh limits and stale-while-revalidate when allowed.
- Preserve last good data with a stale badge; never relabel it as current.
- Don't fetch on every pointer movement, animation frame or React render.
- Validate upstream response schema and allowlisted URLs.
- Select NWS/Open-Meteo availability by capability, not by pretending both return identical fields.

Weather improvements worth shipping:
- Hourly wind/gust charts for saved locations.
- Forecast precipitation amounts, probability and type shown separately.
- Radar playback with timestamps and clear coverage masks.
- Official alert polygons and text, including update/cancellation/expiry handling.
- Pressure trends with consistent pressure reference and sample interval.
- Visibility, snow, heat/cold and smoke context where reliable sources are available.
- A clear selected-location indicator so users know where the weather applies.
- A daily peak chance must not be labeled as the chance at the current hour.

11. DYNAMIC 3D CLOUDS

Visual goal:
Clouds form coherent volumes above the terrain, thicken and evolve smoothly, move in a geographically meaningful way, and blend between weather samples and time frames. Rain/snow effects respond to actual precipitation products. Users can inspect the map underneath.

Scientific boundary:
A radar image alone cannot reconstruct cloud shape, base, top or density. Rain can differ substantially for the same reflectivity, and many clouds produce no precipitation. Treat cloud geometry as a weather-informed visualization unless measured/model height information supports it. Label the mode "Modeled clouds" or "Illustrative storm volumes" as appropriate.

Use two clearly separated modes:
1. Cloud atmosphere: cloud cover by layer drives volume coverage; available height and wind data constrain placement and motion.
2. Radar storm visualization: radar/QPE drives a stylized precipitation volume/effect. If cloud heights are absent, display that limitation; do not call the volume a measured storm structure.

Continuous fields, not isolated cloud objects:
- Build a world-anchored density function over horizontal location, height and time.
- Cloud cover controls occupancy/envelope.
- Cloud base/top or documented layer assumptions define vertical profiles.
- Seeded low-frequency noise gives coherent shape; finer noise erodes edges.
- Precipitation intensity controls rain shafts, particle density and optional illustrative storm darkness.
- Do not derive storm height or severe status solely from rain intensity.
- Overcast without rain and isolated rain within broader cloud cover must both work.

Conceptual density:
  density(x,y,z,t) =
    cloudEnvelope(x,y,t) *
    verticalProfile(z, base, top) *
    coherentShapeNoise(worldPosition, t)

Keep normalized input fields and rendered density separate. Tests inspect source fields; artistic noise must not alter numeric readouts.

Intensity styling:
Use a continuous transfer function, such as log1p(rate), with a small number of configurable visual control points. Suggested developer fixture rates: 0, 0.5, 2, 10 and 30 mm/h. These are rendering samples, not universal meteorological categories.
- Zero rain: no precipitation effect; clouds may still exist.
- Increasing rate: more visible/dense precipitation shafts and particles.
- Optional darker visual profile must be labeled artistic, not a cloud measurement.
- Snow/freezing rain require product/type support, not a temperature-only guess.
- Never create lightning merely because reflectivity is high; use a suitable lightning/alert product or omit it.

Spatial coherence:
- Reproject input into a common georeferenced grid with an explicit mask.
- Sample across neighboring tiles with halos/shared edges.
- Anchor noise to world coordinates, not screen pixels or per-tile random seeds.
- Normalize overlapping volume contributions so seams do not become darker.
- Interpolate numeric quantities before visual mapping where appropriate.
- Respect dBZ's logarithmic nature; any linear-reflectivity mixing or rate conversion needs a documented method. Prefer a supplied precipitation-rate product.
- Never blend no-data into zero rain or clear sky.
- Keep authoritative radar separately viewable so cloud smoothing cannot hide details.

Temporal coherence:
- Use persistent seeds and stable frame identity.
- Interpolate adjacent compatible data frames with validity limits.
- Use altitude-appropriate winds for cloud motion when available.
- Surface winds are an approximation, not upper-cloud winds.
- Wind is conventionally reported as the direction it comes from. Test conversion to motion vectors.
- Radar feature motion can come from a validated optical-flow estimate; it is not interchangeable with surface wind.
- Advect previous/next fields for smooth transitions, then reconcile with the next frame to prevent unbounded drift.
- Do not smear storm cells indefinitely, invent missing frames or continue moving stale weather while presenting it as live.
- Extrapolation, if added, is a separate short-horizon nowcast with a time limit and uncertainty label.

Rendering approach:
- Retain MapLibre; start with a small custom 3D layer using its documented interface for the installed version.
- First prove camera, coordinates, projection, depth/occlusion and lifecycle with a simple known volume.
- Then implement low-resolution raymarching of local cloud slabs/volumes using procedural density.
- Use camera-relative/local coordinates to reduce precision problems.
- Account for latitude-dependent Mercator scale; do not use one fixed meters-to-world conversion nationwide.
- Explicitly declare supported map projections. Keep globe support out of the first milestone unless verified.
- Reconcile real altitude with terrain exaggeration; data stays in real units while display transformation is explicit.
- Test near-plane intersections, viewing inside clouds, camera below clouds, mountains intersecting cloud layers and high-latitude coordinates.
- Shared-depth availability and terrain behavior must be established by a spike. If the installed renderer cannot expose reliable depth for the chosen approach, use a documented compatible offscreen/depth strategy or reduce scope. Do not fake success.
- Render cloud color in premultiplied-alpha form, composite consistently and preserve map GL state.
- Start with simple sunlight/ambient shading. Add expensive multiple scattering or shadows only after profiling.
- Keep ordinary map labels, navigation cues and critical overlays legible. Provide cutaway/fade-near-focus controls.
- Restore/clean buffers, shaders, textures and event listeners on style changes, unmount and WebGL context loss.
- Do not recreate the map or rebuild textures every animation frame.
- Use a worker to prepare density fields and decode data; only bounded uploads reach the GPU.
- Pause visual animation when hidden, reduced motion is requested or the layer is off.

Quality ladder:
- Off: conventional map, radar and numeric weather remain fully usable.
- Low: 2D cloud coverage or inexpensive layered visualization, explicitly identified.
- Balanced: true low-resolution volumetric raymarching in a bounded visible region.
- High: more samples/resolution, optional temporal reconstruction and richer shading.
- Auto: measured frame-time/texture capability selection with hysteresis to avoid oscillation.

Prototype tuning values, not guarantees:
- Balanced: half-resolution target and approximately 32–48 ray steps.
- High: approximately 64–96 steps only where measured performance permits.
- Limit active weather textures by bytes and frames, not just object count.
- Aim for a 30 fps floor on the agreed modest-device fixture; target 60 fps on capable desktops.
- Initially budget roughly 128 MiB of additional weather GPU resources for balanced desktop mode; choose lower mobile limits through measurement.
- Reduce render scale, ray steps, view radius and update cadence in that order as appropriate, without dropping track recording or map interaction.
- Record real measurements and tune these budgets; the owner's powerful desktop is not the only target.

Temporal reprojection, if used, must reject history after discontinuous camera/time/quality changes and avoid ghost trails. A simpler stable renderer is preferable to a fast but misleading smeared storm.

Cloud acceptance fixtures:
- Clear sky, dry overcast, light rain, intense precipitation, snow, overlapping cloud layers.
- Clouds without radar echoes; radar data without cloud-height information.
- Missing data patch, tile seam, irregular frame spacing, stale feed, provider outage.
- Moving storm across a tile boundary; changing wind through 359/0 degrees.
- Mountain cloud intersection, Alaska high latitude, Hawaii, antimeridian viewport.
- Repeated layer/style toggles, context loss/recovery, low-memory fallback.
- Animation pause/scrub/restart remains deterministic for a fixed seed/time.
- Measured frame-time and memory reports on modest hardware.
- Severe alerts and navigation remain readable with dense clouds enabled.

Do not mark this feature complete after implementing only sprites or a static cloud texture. A low-quality fallback may use them, but balanced/high must meet the actual 3D-volume requirement.

12. ADDITIONAL FEATURES TO PRIORITIZE

A. Hunt workspaces
Group marks, routes, tracks, notes and downloaded areas by trip. Add tags, folders, favorite layers and a trip checklist. Preserve cross-project search and export. A project is not tied to one state.

B. Better field notes
Photos, scouting observations, species/activity tags, timestamps and optional weather snapshots. Private by default. Mark water observations with dates so a historic water point is not presented as current availability.

C. Terrain scouting
Slope, aspect, elevation profile, contours and optional terrain viewshed. Compute locally from permitted DEM data where possible. Label DEM resolution and distinguish terrain visibility from vegetation visibility. Do not claim full line of sight through trees.

D. Wind and approach planning
Wind timeline at saved stands; show an approximate downwind sector and comparison to a planned approach. Explain that ridges, thermals and vegetation create local variation. Avoid a scientifically unsupported "animal detection radius" or guaranteed scent simulation.

E. Public access and closures
Highlight trailheads, parking, gates, agency closure polygons and seasonal road status where verified. Record last checked time. Do not infer open access because a line exists on a map.

F. Offline trip readiness
Before leaving, show missing map dependencies, package coverage along the route, available storage, track recording status, cached weather age and backup availability. Make it a practical readiness screen, not a generic warning wall.

G. Portable sharing
Export selected content, a complete backup, and a printable map with scale, north arrow, coordinates, source dates and attribution. Hide sensitive locations by default. Avoid mandatory accounts.

H. Search improvements
Search coordinates, places, units, saved content and offline package indexes through one entry point. Use disambiguation for repeated unit numbers across jurisdictions. Preserve explicit-submit behavior for public Nominatim; do not turn that endpoint into autocomplete.

I. Optional sync
Later add an opt-in sync design with conflict handling, deletion tombstones, offline edits and account/export deletion. Local use stays functional without an account. Choose the threat model and recovery behavior before promising end-to-end encryption. Do not invent encryption protocols.

J. Optional trail-camera support
Start with local file/photo organization by camera waypoint. External camera-service integrations require supported APIs and rights. Do not promise access to proprietary camera clouds.

K. Provider/data health
Show layer provenance, version, coverage gaps, outages and a way to report map errors. Keep detailed diagnostics in a separate panel.

Defer generalized AI chat, opaque animal-location predictions, competitive social feeds and satellite imagery subscriptions. They add cost and complexity before solving the core field use case.

13. COST AND FREE-TO-USER DESIGN

Free software does not eliminate imagery licensing, hosting, bandwidth, GIS maintenance, mobile distribution or signing costs.

Keep these core capabilities free: map viewing, saved content, permitted offline maps, recording, ordinary forecasts, settings and import/export. Do not require paid credentials for the basic app. Optional bring-your-own sources must not break the free baseline.

Maintain a source register:
- Provider/product and official documentation.
- Viewing, caching, bulk download and redistribution rights.
- Authentication and public rate policy.
- Geographic/time coverage and update frequency.
- Attribution and license requirements.
- Estimated request/transfer volume.
- Fallback and exit strategy.

Verify terms before shipping, including existing sources. Open-Meteo's current free endpoint is for non-commercial use and has request limits. A free-to-user app with advertising can still fall outside those free-service terms. Do not assume provider limits can be avoided by distributing requests across clients.

Estimate operating costs with a transparent model:
  weather requests = active users × active sessions × refreshes × uncached spatial samples
  transfer = downloaded packages + viewed tiles + weather frame bytes
  storage = retained map versions + weather history + optional user sync

Show assumptions for small, medium and large usage scenarios; obtain actual provider/hosting prices when implementation reaches that decision. Use CDN/object-storage tile delivery and shared caching only if their measured benefit justifies the service. Establish spending limits and gracefully reduce expensive visual refreshes without damaging saved content.

If open-sourcing, ask the owner to choose an appropriate project license before adding one. Keep third-party licenses and attribution. "Free to use" and "open source" are separate decisions.

17. MAP DESIGN AND RENDERING REQUIREMENTS

Design objective
Make Fieldline feel like a modern outdoor atlas built for exploring terrain. Prioritize readable landforms and useful field information. Avoid a generic road-map appearance, excessive outlines, muddy imagery and indiscriminate visual effects. This section incorporates the owner's follow-up request for every proposed design improvement.

The appearance diagnosis is based on source review, not a completed visual comparison of the running application. Capture real baseline screenshots before changing styles; use them to verify which suspected problems occur at each location and zoom.

Concrete current-code improvements
- store.ts defaults publicOpacity to 0.62. Start visual trials around 0.15–0.25, then tune against real imagery. Preserve existing user overrides; apply changed defaults only to new profiles or explicitly selected presets.
- buildStyle in MapCanvas.tsx draws substantial dark casings and bright white unit/state outlines. Reduce default prominence and emphasize selected units or boundaries in an inspection mode. Maintain enough contrast for actual field use.
- overlayPaint favors orange/yellow major roads. For hunting/scouting styles, emphasize trails and access routes while keeping highways legible but quieter. Do not imply that visually emphasized routes are legally accessible.
- unit-labels enables text-allow-overlap and text-ignore-placement. Replace indiscriminate overlap with collision handling, priority rules and selection-aware labels.
- The street-style land fills cover mainly water, woods and parks. Add supported land-cover categories rather than leaving broad landscapes as a uniform background.
- Topo uses pre-rendered USGS raster tiles. Keep that useful reference option, but introduce a signature vector topo style whose contours, labels and fills can be controlled independently.
- Hillshade currently composites above imagery/land-management color and uses strong shadow settings. Tune relief strength by basemap; do not darken satellite terrain indiscriminately or treat artistically useful shading as actual sunlight.
- Replace numeric layer-array slices such as overlay.slice(3, 11) with explicit named groups and stable layer IDs. Adding one layer must not silently change unrelated draw order.

Three complete map styles

Fieldline Terrain — signature default for new profiles
- Natural earth colors, restrained elevation tinting, crisp relief, blue waterways and clear trails.
- Fine minor contours, stronger index contours and elevation labels following contour lines.
- Contours have their own opacity/visibility controls, independent of hillshade and 3D terrain.
- Show forest, shrub/brush, grassland, wetlands and exposed ground only where supported by actual source classes. Keep classification provenance and date available.
- Use a muted ownership fill or boundary treatment; reserve strong accents for selected features and personal content.
- Make this attractive and useful without satellite imagery.

Fieldline Satellite
- Keep imagery visible beneath minimal overlays, restrained land-management colors and readable labels.
- Include independent controls for ownership boundaries/fills, contours and relief.
- Add an imagery selector with source name, coverage, capture date when supplied, and native resolution where reliable.
- Compare the existing Esri imagery with permitted USGS NAIP or other verified sources at representative locations. Select by evidence, not a blanket claim that one provider is always sharper.
- At unsupported zoom, disclose the source limit; do not present enlarged pixels as new detail.
- Handle imagery mosaics with multiple dates; do not invent a single date for the entire viewport.

Fieldline Field
- High-contrast, simplified presentation for outdoor phone navigation.
- Larger controls, clear location/accuracy/heading, a readable current route, essential landmarks and quiet supporting detail.
- Works in 2D with expensive effects disabled; terrain/clouds are optional.
- Night mode preserves category distinctions and readability, rather than merely inverting colors.

Shared design system
Define tokens for background/land, water, vegetation, minor/index contours, minor/major roads, trails, management boundaries, selected features, recorded/planned routes and warnings. Give each style corresponding values rather than scattering arbitrary color constants through components.

Use a small consistent icon family for gates, trailheads, parking, camps, water, glassing spots, stands, cameras and ordinary pins. Preserve meaning through shape as well as color. Cluster nearby markers at broad zooms, display counts, and offer an accessible expansion/list interaction. Keep the active destination visible when other markers cluster.

Detail and label hierarchy
- At national/regional scales, emphasize the landscape and major place context.
- At local scales, introduce major contours, drainage names, primary trails and selected unit context.
- At close scales, add finer contours, springs, gates, smaller trails and supporting labels where data is available.
- Derive thresholds from readability and data resolution, not arbitrary duplication across layers.
- Prioritize selected content, navigation, meaningful terrain names and then background labels. Reduce collisions without hiding the active destination.
- Label density, contour intensity, text size and marker size must be configurable.
- Distinguish small intermittent waterways from perennial water if the source supplies that classification. Do not infer current water availability from a map symbol.

Terrain presentation
- Provide smooth tilt/orbit controls, one-action north-up/2D reset, optional atmospheric sky/depth and adjustable terrain exaggeration.
- Evaluate supported multidirectional relief for general terrain readability; keep a separate sun-linked mode.
- Verify the installed MapLibre version and APIs before using examples from newer documentation.
- A sun-direction hillshade is not a terrain cast-shadow calculation. Name it accordingly. Actual cast shadows require a separately validated DEM horizon/occlusion computation.
- Preserve real elevation/analysis values regardless of display exaggeration.
- Avoid fake 3D trees or vegetation detail inferred from coarse classifications. Do not use generated or AI-enhanced imagery to invent trails, structures or vegetation edges.

Render stack and loading
Use named semantic groups: base imagery/land, relief/contours, thematic fills, roads/trails/water detail, boundaries, ordinary labels, personal content, navigation and inspection highlights. Adapt final ordering to tested readability; avoid duplicate labels from raster and vector sources.

Keep ready tiles visible while replacements load when supported. Use bounded transitions, keep the camera stable when changing styles, preserve selection, and provide layer-specific errors. If a displayed tile is stale, retain its age metadata. A style transition must not silently display old ownership data as a freshly loaded source.

Prevent map reconstruction when toggling a layer or changing its opacity. Reuse sources where appropriate, cancel obsolete requests and dispose unused resources. Respect reduced-motion settings. Test rapid zoom/style changes, failed tiles, low bandwidth and restoration of a previously selected style.

Inspection and comparison
- Add a clean inspection mode that hides panels and optional overlays while keeping essential location/recording status and attribution available.
- Provide a press-and-hold original-imagery reveal control, with an equivalent toggle for keyboard/touch accessibility. Restore the exact previous state on release, cancellation or lost focus.
- Add a synchronized side-by-side terrain/imagery view and a swipe comparison between compatible imagery sources/dates.
- Share camera center/zoom/bearing/pitch where both views support them; prevent event feedback loops. Use 2D when a comparison cannot align reliably in 3D.
- Display each side's independent dates, source and missing coverage. Do not compare mismatched views without telling the user.
- Restrict the visible/rendered workload on modest devices; never degrade recording for a comparison animation.

Selection focus
Selecting a route, unit or parcel highlights it and temporarily reduces distracting overlays. Make the effect adjustable and reversible. Do not hide critical closure/alert information. Normal map clicks, deselection and saved settings must behave consistently.

Map recipes
Users can save named layer/style configurations such as Find water, Plan an approach, Check access or Glassing. A recipe includes style, active layers, opacity, label density, contour/terrain settings and optional camera defaults. It does not duplicate user content or bypass provider restrictions. Version recipes and validate them on import. Unsupported layers remain listed as unavailable, rather than silently disappearing.

Design acceptance
Maintain a before/after gallery at fixed views in Arizona desert, forested mountains, an eastern rural area, a town, Alaska and Hawaii, with multiple zooms and narrow/wide layouts. Review daylight/night/high contrast, selection, poor network and offline states. Confirm readable boundaries, collision-managed labels, distinct icons and original imagery fidelity. Record the owner's visual feedback when available; do not let subjective polishing block objective field reliability.

18. SCOUTING WORKSPACE AND TERRAIN TOOLS

Core workflow
Choose an area or route corridor -> compare terrain and imagery -> inspect candidate spots -> save viewpoints and observations -> sketch approaches -> inspect wind/daylight -> download the trip -> record and review the field visit.

Extend existing hunt workspaces rather than creating a second competing project system. A workspace spans jurisdictions and contains references to waypoints, planned routes, recorded tracks, views, notes, photos, map recipes, analyses and offline packages. Preserve navigation between Map, Plan, Observations and Downloads without resetting map context.

Scout this spot panel
Click/tap a location to show coordinates, elevation, slope, aspect, land ownership/management/access context, nearby mapped access points and weather. Show data dates/resolution, unknown values and estimated calculations. Link to source/agency details. Nearby means geographically nearby, not necessarily reachable or publicly accessible. Keep expensive analysis cancellable and cache it by input/source version.

Route drawing and linked profiles
- Support freehand/manual route vertices and optional snapping only to a supported routing network.
- Show distance, ascent/descent and a sampled elevation profile as the route changes.
- Hover, tap or keyboard-focus a profile position to highlight the matching map location; selection on the route can focus the profile.
- Distinguish horizontal distance, optional terrain-following length, elevation gain and estimated travel time.
- Filter DEM noise for ascent totals using a documented sampling/smoothing policy. Keep original inputs, resolution and gaps available.
- Mark missing elevation spans instead of drawing fictitious flat terrain.
- Bound recomputation, debounce editing and run large calculations off the main thread.

Terrain cross-section
Draw a line across a canyon or ridge to inspect a terrain profile, local slopes and total elevation difference. Reuse route-profile calculations and rendering, with a separate analysis entity when the line is not a travel route. Support units, vertical exaggeration and clear horizontal/vertical scales. This is topography, not underground geology. Test known synthetic slopes, flat terrain, gaps and long sections with geodesic sampling.

Glassing coverage and viewsheds
- Let a user choose a viewpoint, observer height above ground, target height and maximum analysis range.
- Compute terrain visibility from a specified DEM. Display visible, terrain-occluded and unknown areas, with the calculation's resolution and source date.
- Compare multiple viewpoints and optionally show their coverage union/intersection.
- Keep vegetation/building obstruction separate. If no canopy/surface model exists, label results terrain-only.
- Record assumptions about earth curvature/refraction for longer ranges; do not promise exact visibility from coarse elevation data.
- Use workers, cancellation, tiling and explicit memory/range limits. Start with a bounded local analysis rather than an entire state.
- Test a flat plane, isolated ridge, valley, observer behind a ridge, no-data cells and overlapping viewpoints. Cache by viewpoint, observer/target heights, range, algorithm version and DEM version.

Return-trip planner
Use a selected route, reverse recorded track or explicitly labeled straight-line estimate to calculate distance, climbing and an estimated travel-time range back to camp/car. Compare arrival with astronomical sunset/twilight at the destination; do not confuse this with legal shooting hours.

Let users set walking pace and optionally calibrate it from their own recorded moving time, grade and terrain context. Exclude pauses, vehicle segments and poor GPS samples from calibration. Explain the sample basis and allow reset/manual override. Do not promise safe passage or a guaranteed arrival time; show missing access/elevation/weather inputs. Test time zones, midnight crossing, polar day/night and incomplete return routes.

Saved camera views
Store camera center, zoom, bearing, pitch, optional terrain exaggeration and associated location/project. A view may reference a map recipe without freezing all user preferences. Restore gracefully when its original source is unavailable. Support naming, ordering and comparing canyon/hillside approach views. Views do not replace waypoints and must export in the full backup.

Directional photos
Attach photos to viewpoints/waypoints with capture time, optional position, heading and heading reference, plus field notes. Read metadata only with user awareness; allow manual correction. A location/heading can restore an approximate viewpoint, but exact camera reconstruction requires additional calibration and must not be claimed from an ordinary photo. Preserve the original photo; store thumbnail/derived metadata separately. Strip sensitive location metadata from shared copies by default unless the user chooses otherwise.

Personal scouting history
Filter user observations by date, season, year, species/tag, project and location. Distinguish observation time from entry time. Support comparing visits to the same area and viewing attached photos/weather snapshots. Clearly distinguish user observations from imported records and model estimates. Do not turn sparse observations into authoritative animal-location predictions. Local journals and filtering are required; an AI prediction service is not.

Synchronized scouting timeline
Coordinate selected time across sun direction, modeled weather and wind for a saved stand/viewpoint. Retain observed/forecast boundaries and display time mismatches when products do not cover the same instant. Missing historical weather must remain missing rather than being filled with today's forecast. Use the weather timeline contract from Section 10 instead of a second independent clock.

Offline coverage and trip readiness
Show downloaded-package boundaries on the map with usable zoom ranges and per-layer completeness. Evaluate coverage along planned approaches and the return route, including gaps in terrain, labels or identify data. Distinguish current-view coverage from deeper-zoom coverage. List cached weather age, storage headroom, active recording state and backup status before a trip. Read the actual verified package manifest; never infer readiness from cached tile counts alone.

Custom map data
Extend imports to preserve semantic geometry types: points remain waypoints; route lines remain routes; areas remain polygons instead of being silently converted to tracks. Accept a defined, documented subset of GeoJSON/KML/GPX first, with other GIS formats gated by reliable parsers and coordinate-transform support.

Let users style imported layers by category, color, line width, fill opacity and labels without coding. Validate coordinate reference systems, geometry and bounds; reject or explicitly transform supported non-WGS84 data. Preserve source/date/rights fields when supplied. Treat a user-imported survey as a reference, not proof of current legal ownership. Large files need feature/byte limits, worker parsing, spatial indexing and appropriate simplification or tiling. Restrict remote resource loading in imports. Include local layers in backup and allowed offline packages.

Undo and recovery
Implement reversible commands for marker moves/deletes, route vertex edits, note edits and imported-layer changes. Group continuous drags into one undo step. Provide redo and persistent recoverable trash for deleted personal content, with documented retention and explicit permanent deletion. Restore attachments and project relationships with the parent item. Test interruption between delete/restore operations, undo after imports, migration compatibility and storage exhaustion. Cache eviction must not empty personal-content trash.

Workspace acceptance
Create a trip spanning two jurisdictions, compare imagery with terrain, save two views and a directional photo, draw an approach, inspect its profile, run a bounded viewshed, estimate the return before dusk, add dated observations, undo a mistaken deletion, import a polygon, download a permitted package and reopen offline. Restore the complete workspace from backup and confirm IDs, relationships, styles and attachments survive. Every requested tool must be functional rather than a placeholder.

20. FIELD RELIABILITY AND MAINTENANCE REQUIREMENTS

This section turns the final follow-up recommendations into required engineering work. Extend the existing storage, catalog, navigation and distribution systems; do not create duplicate implementations. A minimum complete release is an earlier milestone, not a reduction of the full master-document scope.

REL-01 — Minimum complete app
The first useful release must combine settings, polished nationwide map navigation, honest per-layer coverage, saved waypoints, reliable supported-platform tracking, verified permitted offline downloads, full backup/restore and the existing ordinary forecast capability. Nationwide navigation does not mean every national dataset is complete.

Acceptance journey: install on a supported platform; configure units/map style; search across jurisdictions; save camp and destination; download a permitted area; close the app; disable networking; relaunch; navigate within the package; record and recover a track; export a full backup; restore it into a clean profile; update to the new app version without losing content. The user can see unavailable layers, old forecasts and uncertain positions throughout.

Block core release for data loss, false offline-ready states, misleading ownership results, broken installation, or failure of advertised recording behavior. Advanced viewsheds, imagery history and clouds must not postpone this milestone once its own gates pass. They remain required later work packages where specified elsewhere.

REL-02 — Early phone architecture decision
Desktop remains a planning platform. Determine how the actual phone field experience will work before substantial platform-specific development. Evaluate PWA and, where needed, a native-capable mobile shell with explicit background-location/storage support. Do not assume a shell automatically solves either problem.

Record target operating systems/devices, intended recording duration, foreground/background requirements, permissions, offline storage behavior, location-plugin maintenance, distribution costs and shared-code boundaries. Use a short working prototype to test the highest-risk capabilities. Verify current platform documentation during implementation; do not choose based solely on framework marketing.

Select the simplest architecture supported by the evidence. Reuse domain models, provider adapters and migration/backup formats through platform interfaces. Keep device-specific location and storage code out of map components. Do not wait until the cloud renderer is finished to discover that recording cannot meet the field requirement.

REL-03 — Real-device field test program
Maintain a device/OS/build matrix with supported, limited, unverified and unsupported capabilities. Include actual iOS and Android devices intended for support; emulators and desktop browser tests supplement but do not replace physical tests.

Required scenarios: airplane mode; screen locked; app backgrounded; incoming call/interruption; weak or stale location; denied/revoked permission; battery saver; low storage; network loss/recovery; app process terminated; phone restarted; long/overnight session; upgrade with saved content. Test background continuation separately from recovery after force termination: do not promise an OS will continue a deliberately terminated process.

For each run record device/OS, build, duration, settings, starting/ending battery, recording gaps, fix accuracy, recovered points, storage failures and exact steps. Keep sensitive tracks local or use a consented/redacted test export. Agree measurable duration, acceptable gaps, checkpoint-loss bounds and battery expectations for the target devices before certification; do not invent universal battery-life guarantees.

Acceptance: advertise only demonstrated combinations of platform and behavior. Missing devices are explicit pending tests. When hardware is unavailable, the coding agent must deliver an installable build, test instructions and a result template, and complete all other authorized work without pretending the field test passed.

REL-04 — Data maintenance ownership
Extend docs/data-sources.md with a responsible maintainer/contact or explicit unassigned status for each production adapter, refresh cadence, last fetch, last successful validation, upstream publication date, license-check date, expiry policy and failure escalation. These timestamps mean different things and must remain separate.

Use automated health checks for endpoint/schema changes, freshness, coverage and unexpected geometry/count changes. Cadence is source-specific; respect request limits and avoid polling static annual data like live weather. An automated successful download alone must not become a human-reviewed legal/access verification date.

Expose source freshness and outages in the app. Provide a practical maintenance runbook with steps to diagnose, disable, replace and restore a provider. Do not silently assign a real person or send them notifications without authorization. Owner assignment is a documented project responsibility, not something the coding agent can fabricate.

REL-05 — Protected source-data promotion
Download updates into staging. Validate schema, CRS, geometry, paging completeness, source version, expected coverage and provider-specific count/area changes. Flag suspicious changes for review; thresholds are anomaly checks, not proof of correctness. Large legitimate changes must remain reviewable.

Quarantine failed or anomalous updates and retain the last known good published dataset with an accurate stale label. Promote valid versions atomically and retain enough metadata/checksums for rollback. Never let an empty HTTP-success response silently erase known coverage. Keep user content separate from provider-data rollback.

Acceptance fixtures: renamed field, truncated pagination, empty success, malformed geometry, large boundary revision, source unavailable, interrupted promotion and rollback. Verify both online catalogs and previously downloaded packages remain internally consistent.

REL-06 — Boundary uncertainty display
Show location fix age and horizontal accuracy together with boundary/source information. Use neutral language when a fix is old, poor, missing or too close to a boundary to confidently identify a side. An accuracy circle is an estimate supplied by the platform, not a guaranteed enclosure.

Do not equate source resolution with boundary positional accuracy. If the source publishes uncertainty, preserve it; otherwise record unknown. An optional conservative display buffer must be labeled a visualization setting, not a measured legal margin. Never produce precise crossing probabilities without a validated statistical model.

Near-boundary alerts should use configurable hysteresis/dwell behavior and accuracy-aware logic to reduce repeated false crossings. Keep potentially relevant boundary warnings visible even when certainty is low. Test jitter across a line, stale fixes, unknown source accuracy, multiple nearby boundaries and loss of coverage. The app reports uncertainty rather than deciding legal access.

REL-07 — Offline emergency information screen
Provide a large, accessible screen reachable from the main field UI: latitude/longitude, explicit coordinate format and WGS84 reference where applicable, fix timestamp/age, horizontal accuracy, current versus last-known status, and saved camp/car coordinates. Include copy/read-aloud-friendly labels and an optional local personal emergency note.

Work offline using locally stored information; distinguish unavailable current position from last known position. Update fix-age text even without fresh GPS. Do not silently substitute map center for the user's location. Display coordinate signs/directions clearly and prevent accidental format ambiguity.

This screen does not contact rescuers or provide satellite communication. Any future calling/messaging integration requires real platform capability, explicit user action and accurate connection/delivery status. Do not put a nonfunctional SOS control in the app.

Acceptance: launch offline with a fresh fix, stale fix, no permission and no saved fix; verify correct labels, legibility, coordinates and camp/car access. Test large text, screen reader navigation and one-handed use.

REL-08 — Upgrade and recovery release gate
Build populated fixtures from every supported previous schema/release: settings, waypoints, tracks, active-session checkpoints, projects, photos, imported layers, saved views/recipes, trash and package references. Install the candidate over the old app and verify identity/relationships/content, not just record counts.

Exercise interruption, full storage, corrupted source records and migration failures. Preserve original data until commit/verification. Test backup restoration in a clean profile. An older binary must not silently open and overwrite an unsupported newer schema; provide recovery/export or a clearly supported compatibility route instead of promising arbitrary downgrade safety.

Document the supported upgrade paths and maximum recovery/checkpoint loss observed. No release passes because only a clean install or web build succeeded. Package manifests, app-shell caches and source catalogs must survive updates without falsely remaining ready after dependencies change.

REL-09 — Reviewed map-error reporting
Let the user flag a trail, boundary, access record or missing feature from its inspection panel. Prepare a report with selected feature/source ID, source version/date, coordinates or chosen extent, category, user description and optional evidence. Show a preview and allow redaction before any submission. Reports are private unless the user explicitly shares them.

Provide a local draft/export workflow when no service is configured; do not introduce a cloud account requirement just for reporting. Connected submission is optional and requires an actual receiving/review workflow. Track draft, submitted, under review, resolved or declined status without falsely claiming external review occurred.

Reports never directly overwrite authoritative datasets. A maintainer can investigate against agency/source evidence and publish a reviewed adapter/data correction. Preserve a decision history. Distinguish a user's local annotation from a confirmed map correction. Test offline drafting, retry/deduplication, failed submission, privacy redaction and source-version changes.

REL-10 — Contributor adapter kit
Deliver a small adapter template, documented contracts, example configuration, source-register entry, provenance/license checklist and a reproducible validation command. Include representative source fixtures and test cases for pagination, schema drift, empty responses, coordinate transforms, duplicate IDs, coverage masks and unknown values.

Use the existing Arizona/Idaho migration as a reference adapter and demonstrate another jurisdiction without changing the app shell. Provide a contributor quick start, fixture-update instructions and instructions for staged validation/promotion/rollback. Live requests remain opt-in and rate-bounded. Ensure CI actually discovers adapter tests outside the legacy src/lib/hunt test glob.

Release evidence and sequencing
